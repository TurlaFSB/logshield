# Assurance: how the project maps to common standards

This page lists the practices the project follows and where the evidence is, so
a reviewer can check rather than trust. It is a self-assessment, not a
certification. Where a practice is only partly met, it says so.

## OpenSSF Scorecard

| Check | Status | Evidence |
|---|---|---|
| Binary-Artifacts | Met | No binaries in the repository or its history |
| Branch-Protection | Met | Ruleset on `main`: pull requests, six required passing checks, up-to-date branches, linear history, no force-push, no deletion (`scripts/repo-settings.sh --protect` recreates it) |
| CI-Tests | Met | [ci.yml](../.github/workflows/ci.yml): unit, race, fuzz smoke, integration, load smoke, three operating systems |
| CII-Best-Practices | Met | "Passing" badge: <https://www.bestpractices.dev/projects/15621> |
| Maintained | Time-based | Scorecard requires the repository to be at least 90 days old; commits are frequent |
| Code-Review | Limited | Single maintainer today; every change is a pull request with passing CI, but human review depends on contributors |
| Dangerous-Workflow | Met | No `pull_request_target`, no untrusted input in `run` steps |
| Dependency-Update-Tool | Met | [Dependabot](../.github/dependabot.yml) for Go modules, Actions and Docker |
| Fuzzing | Met | Go fuzz targets run on every change and weekly |
| License | Met | MIT |
| Packaging | Met | Release archives and a container image published by CI |
| Pinned-Dependencies | Met | Actions by commit SHA, base image by digest, CI Python tools by hash |
| SAST | Met | CodeQL and golangci-lint (gosec, staticcheck, errorlint and more) |
| Security-Policy | Met | [SECURITY.md](../SECURITY.md): reporting link, scope, response targets in days, disclosure policy |
| Signed-Releases | Met | Keyless Sigstore signatures and provenance on every release |
| Token-Permissions | Met | Read-only default; write permissions only on the release job |
| Vulnerabilities | Met | `govulncheck` in CI; no third-party Go dependencies |

## SLSA (supply-chain levels)

Release archives and the container image are built by a hosted GitHub Actions
workflow, with provenance generated by GitHub's attestation service and
verifiable with `gh attestation verify`. That corresponds to **SLSA Build
Level 2**. Level 3 requires the build to run in an isolated reusable workflow
that the project's own steps cannot influence; this is a possible future
improvement, and the project does not claim it.

## NIST SSDF (SP 800-218), summary

| Practice group | How it is addressed |
|---|---|
| Prepare the organization | Contribution rules, threat model, ADRs |
| Protect the software | Branch protection, signed and attested releases, pinned dependencies, secret scanning |
| Produce well-secured software | Fail-closed design, bounded resources, fuzzing, static analysis, differential validation |
| Respond to vulnerabilities | Private reporting, advisories, regression corpus entries |

## Not claimed

No third-party audit, penetration test or certification has been done. The
detection evidence has stated limits ([lab.md](lab.md),
[threat model](threat-model.md)). Anyone depending on LogShield in a regulated
environment should run their own assessment.
